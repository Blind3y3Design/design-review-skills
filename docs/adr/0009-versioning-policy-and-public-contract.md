# One SemVer version for the set, cut against a declared invocation surface

Semantic versioning versions a named interface, and a set of agent skills has no code API, so the interface has to be declared. The set carries one version for all of it ([ADR 0007](0007-publish-skills-exactly-as-released.md)), and that version covers the **invocation surface**: the set of skill names; the required install/discovery set (the Orchestrator hard-fails unless `design-review-profile`, `design-review-scanner` and `design-review-report-writer` are present); each skill's trigger `description` and the inputs it declares (a Figma file or scope, a Review Profile, handed-over JSON); each skill's declared outputs — the report (schema `schemaVersion`), the Design Facts (`factsVersion`) and the Figma writes; and the Reference-Document URL scheme, pinned per tag. Internal wording, code structure, and report prose as opposed to the report *schema* are not the contract.

**Bump triggers.** **MAJOR** is breaking: rename or remove a skill; remove an input a caller supplies; add a hard dependency to the required install set; an output change that breaks a consumer; a breaking `schemaVersion` or `factsVersion` change. While the set is `0.y.z` a breaking change bumps the **minor** (`bump-minor-pre-major`); from `1.0.0` it bumps major. **MINOR** is additive and behavioural: a new skill; a new optional input; additive output or report fields; a new capability; a deprecation notice; and a material change to a skill's trigger description or instructions that changes behaviour without touching declared inputs or outputs. **PATCH** is a fix with no behaviour change: typo, clarification, internal reorder, prose-only edit. A behaviour-affecting fix ships as `fix` and cuts a PATCH release; a pure typo or clarification ships as `docs` and cuts no release, riding into the next release that happens.

**`schemaVersion` / `factsVersion`.** They keep their own axes and change only when a field's format or meaning changes, never with a release ([ADR 0007](0007-publish-skills-exactly-as-released.md)). Any change to either ships in a set release and forces a matching-magnitude set bump in the same release: breaking to MAJOR (minor while `<1.0`), additive to MINOR, so a report never names a schema the set's version doesn't cover.

**Lifecycle.** One version for the whole set, `0.y.z` until `1.0.0`. The owner declares 1.0 at the first release where all planned Review Skills exist, the smoke suite passes fully in both runtimes (external agent and Figma), there are no known breaking gaps, and the set is published to the organisation's Figma file. 1.0 is explicitly not tied to the research axis ([#50](https://github.com/Blind3y3Design/design-review-skills/issues/50)).

**Pre-release scheme.** `-dev` is dropped: it sorts between `beta` and `rc`, and it has no place to live once `main` always shows the last released version — the next version exists only as the standing Release PR, never stamped on a branch. Pre-releases use `-alpha.N`, `-beta.N` and `-rc.N`, each marked `prerelease: true`: alpha is incomplete or exploratory, beta is feature-complete for the target, rc has no known blockers. They order correctly against each other and against the final release.

**Deprecate, rename, remove.** A skill is deprecated in a MINOR: still installed, still working, marked deprecated in its `description` and in the docs. It is removed no earlier than the next MAJOR, giving at least one stable release of grace. A rename is a remove of the old name plus an add of the new, under one MAJOR, so a caller discovers it as one breaking change.

## Consequences

- An unpinned consumer installing from the default branch receives exactly the last release at exactly its stamped version; that invariant is why `main` mirrors the release tag (ADR 0010).
- Pure documentation commits cut no release. The changelog and the release notes come from Conventional Commits, so `docs:` carries nothing and the next release that does happen picks the clarification up.
- While the set is `0.y.z`, a breaking change is a minor bump: 0.x consumers must read the changelog for breakage, which is the accepted cost of staying pre-1.0.
- A `schemaVersion` or `factsVersion` change and the matching set bump ship together in one release; neither is ever stamped alone.
- Deprecation gives consumers a full minor release of notice before removal, and a rename never strands the old name silently.
