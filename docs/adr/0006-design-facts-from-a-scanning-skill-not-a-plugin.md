# Design Facts come from a scanning skill; a plugin is never the delivery path

Design review is delivered by the Orchestrator and Review Skills, not by a custom Figma plugin. Two independent reviews ([issue #20](https://github.com/Blind3y3Design/design-review-skills/issues/20)) reached this for the same reasons. The review's value is judgement, and a plugin can only reach an LLM through an org-run proxy, because plugin source is readable and can't hold a key, so design data would leave Figma. A plugin also runs only inside Figma, can't use Figma's connectors or read other Figma files, and would drop research alignment. What a plugin does better is read the design the same way every time. We keep that by running all Plugin API code as fixed, tested scripts, each in the one skill whose single job it serves. The Design Scanner reads the scope, measures what code measures well (such as contrast against the computed background), and returns Design Facts, which the Review Skills judge against their Reference Documents. The Profile Finder reads the "Review Profile" page, and the Figma Writer writes into the reviewed Figma file: report frames and layer annotations for the Report Writer, and the Review Profile page for the Orchestrator. The scanner only reads.

## Consequences

- The Design Scanner is two required skills (ADR 0004): if one won't load, the run stops and names it. `design-review-scanner` reads the colour pairs, text, structure and annotations groups, and `design-review-scanner-assets` reads the bindings and components groups. An Orchestrator run scans once, asking each skill once for its groups and joining the results for each node, and passes the Design Facts to every Review Skill. A Review Skill run on its own invokes the scanner skills it needs itself: design system adherence only `design-review-scanner-assets`, accessibility both.
- The Profile Finder is required in the same way. The Figma Writer is needed only to write into the file, to save a report to its report page, annotate layers or save a Review Profile page: without it, the report stays in the chat and says why, and the profile page can't be used.
- The scanner takes the scope as node ids from the agent and fetches each node, because scripts in `evaluate_script` can't see the user's selection. Every script uses top-level `await` and `return`, since an async wrapper loses its return value there ([issue #21](https://github.com/Blind3y3Design/design-review-skills/issues/21)).
- Callers ask for groups of facts, and results come back one top-level frame at a time. The scanner summarises inside the script, grouping by Root Cause with counts and sample node ids, and keeps each call's output to about 18,000 characters: a 17,000-layer page produced 1.85 MB of per-layer facts (#21). The limit is the smaller runtime's: about 58 KB inside Figma's agent, and about 20 kB through `use_figma`. Every result states a `factsVersion`, the scope, the runtime, which groups were read, and anything that couldn't be read.
- **Why two skills.** Figma accepts a skill of at most 65,536 characters, and the one scanner skill, with its six scripts, came to 86,669. The scripts are fixed and tested as written, so none is shortened: the scanner is split by what it reads, with the skill each fact group comes from named in each caller. A scanner asked for a group it doesn't read says so in `unread`, naming the skill that does. `scripts/release.mjs check` fails any `SKILL.md` over the limit.
- `use_figma` also refuses a script longer than 50,000 characters (#43). A write too large for one call is split into parts, or a report frame goes without its JSON, which stays in the chat.
- `figma.teamLibrary` names the library of every variable by its collection key, inside Figma's agent and through `use_figma` alike, so variable attribution is `confirmed` in both runtimes (#21, #35). The Plugin API has no library lookup for components and styles. External agents name them by key through the Figma MCP server's `get_libraries` and `search_design_system` (`confirmed`). Inside Figma's agent they're attributed by name-prefix hints (`likely`).
- The scanner holds no thresholds or criteria. When a measurement can't be made, such as text over an image, the fact says why, and the Review Skill reports it as `needs-review` or as `not-readable` in Coverage.
- A read-only plugin may be added later as another source of Design Facts or as a way to view Findings, never as the reviewer. Either must make no network calls and hold no secrets:
  - **A facts plugin**, if real-file testing shows the scan is too slow. It no longer adds attribution: #21 showed the agent already names variable libraries through `figma.teamLibrary`, and a plugin can't name component or style libraries either. It is also the fallback if `evaluate_script` goes away (ADR 0005).
  - **A Findings panel** that reads the report JSON saved on the report frame, if designers find long chat reports hard to work through.
- Generative plugins can't do the review. Figma documents that they can't call third-party APIs, and their manifest can't be changed.
