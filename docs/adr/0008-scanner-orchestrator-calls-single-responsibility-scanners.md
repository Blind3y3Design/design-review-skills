# The Design Scanner is one orchestrator skill calling six single-responsibility scanners

The Design Scanner is a single skill, `design-review-scanner`, that orchestrates the scan and invokes one leaf scanning skill per fact group: colour pairs, text, structure, annotations, bindings and components. This supersedes the two scanner skills of ADR 0006 ([#74](https://github.com/Blind3y3Design/design-review-skills/issues/74)). The old split was a size artifact with no design behind it: the one scanner skill, with every script and the Design Facts format, came to 86,669 characters against Figma's 65,536-character cap, so it was cut into two skills named after the clusters they happened to hold. That left the group-to-skill map and the join of the two results to every caller, and made each scanner name the other in its `unread`. The new shape follows ADR 0004 instead: one entry point that owns the scan, and small leaf skills that chain, each with one job.

Each leaf skill holds exactly one fixed script and the shape of its own fact group, and nothing else. The scripts are fixed and tested as written, so the leaves move them byte-identical. Each leaf hands the script's result back as the script returns it. The orchestrator owns everything shared: picking the runtime tool, dispatching each requested group to its leaf, following `scanInstead` (a page fans out across all groups; an output limit fans out per group), naming libraries by key for bindings and components, and joining the leaves' results into one result per scanned node with the shared envelope: `factsVersion`, `fileKey`, `scope`, `groups`, `unread` and `runtime`. The Design Facts a caller receives are exactly as the scanning skills returned them, so `factsVersion` 0.5 is unchanged.

## Consequences

- Callers ask the one skill `design-review-scanner` for the fact groups they need and get one result per node. The group-to-skill map and the join instruction leave `design-review`, `design-review-accessibility` and `design-review-library`. A scanner's `unread` no longer names another skill.
- The set grows from eight skills to thirteen. The leaves invoke nothing and are private to the orchestrator: no Review Skill invokes a leaf. Publishing order is leaves first, then the orchestrator, then the Report Writer, then the Review Skills, then `design-review` (ADR 0007).
- A leaf is required only for a group the caller asked for. The orchestrator stops and names a missing leaf only when its group is needed; a missing leaf for an unrequested group does not stop a run. A review always needs its groups, so a missing leaf still stops the review that needs the group, but a run asking for accessibility only does not require the bindings or components leaves.
- The Design Facts envelope is owned once, by the orchestrator. A leaf describes only its own group's shape, so the shared contract can't drift between copies. `factsVersion` and `schemaVersion` change only when a field's format or meaning changes, never with this restructure.
- The design-review skills' character-count headroom stops shaping the architecture. A new fact group in a later release is a new leaf skill.
