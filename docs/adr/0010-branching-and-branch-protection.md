# `main` mirrors the latest release; `integration` stages everything else

The model is decided by a consumer invariant, not by a test battery: `npx skills` installs from the repository's default branch, and git tags are inert unless a consumer pins `#<ref>`. If `main` carried merged-but-unreleased work, an unpinned consumer would receive content stamped with the *last release's* version. So `main` holds released content only — its tip always equals the latest release tag's commit — and `integration` is the staging branch where merged-but-unreleased work accumulates. Short-lived `feature/*`, `ai/*` and `bugfix/*` branches (with `research/`, `prototype/` and `spec/` following the same path) merge into `integration`.

**Release flow.** release-please runs on `integration` (`target-branch`). Merging its Release PR tags `v<version>` **on `integration`** and creates the GitHub Release. A release workflow then **fast-forwards `main` to that tagged commit** — a plain fast-forward push, not a force-push — so `main`'s tip becomes the tag's commit and unpinned consumers see the release. The release App is the only bypass on `main`. **Pre-releases** (alpha, beta, rc) tag on `integration` and are **not promoted** to `main`; a consumer opts in by pinning `#v0.2.0-beta.1`. There is no `release/*` branch on the normal path, because promotion is automatic; `hotfix/*` stays reserved for back-porting a fix onto an older released line, and otherwise the set fixes forward.

**Protection.** One un-filtered CI job is required on both branches — a path-filtered required workflow sits "pending" forever. Linear history is required on both. `integration` is squash-only, so each pull request lands as one commit whose message is its PR title. `main` is rebase/ff-only, never squash, so it can mirror the tag commit. Both require a pull request with 0 approvals while the repo has one owner (ADR 0011). Force-push and deletion are blocked on both. Signed commits are off; the merge queue is off, being unavailable on a user-owned repository. CODEOWNERS runs for awareness only (ADR 0011).

## Consequences

- `main` is safe to install from unconditionally: its content, its stamped version and its pinned Reference-Document URLs are always the latest release's. The old "start the next `-dev` version" step of the release checklist disappears — the next version exists only on the Release PR.
- Unreleased work is visible and reviewable on `integration` instead of living on long-lived feature branches, and nothing on it can reach a consumer.
- Squash-only on `integration` makes the PR title the commit message, so Conventional Commits are enforced on PR titles in CI, which is what release-please reads to cut the next version.
- Pre-releases never disturb unpinned consumers: they are tagged on `integration`, marked `prerelease`, and never fast-forwarded to `main`; the final version reaches `main` as its own release.
- Releasing needs no human push to `main`; the only write to `main` on the release path is the workflow's fast-forward, which is why the release App sits on `main`'s bypass list alone.
- Existing one-off branches are pruned and the `feature/` / `ai/` / `bugfix/` / `research/` / `prototype/` / `spec/` convention adopted (issue [#91](https://github.com/Blind3y3Design/design-review-skills/issues/91)); the rulesets themselves are filed as build tickets.
